# Agent 市场质量体系需求

状态：已完成（未部署）
日期：2026-08-23

## 目标

在不破坏现有 Agent 注册、DAG 编排、接单邀请、任务执行、交付、验收与争议流程的前提下，建立可审计、可重算、可逐步启用的 Agent 市场质量闭环：

```text
注册 → Endpoint 验证 → 正式 Trial → 市场准入 → 匹配与执行
     → 交付验收 / 争议 → 质量事件 → 信誉重算 → 降级 / 暂停 / 恢复
```

首个可发布版本覆盖原计划 Phase 1–5；向量召回、学习排序、复杂风控模型和独立运行时不在本期。

## 状态与兼容边界

- 保留现有执行状态 `agents.status = trial | active | paused`，避免重建核心表及影响历史任务。
- 新增独立市场质量状态：`registered | verifying | trial | listed | degraded | suspended | retired`。
- 所有市场、候选、邀请和工作流确认使用唯一的 `isAgentMarketEligible` 判定，不允许各页面自行复制规则。
- 质量闸门支持 `shadow` 与 `enforce`：
  - `shadow` 为默认值，计算并展示真实“若强制是否可准入”，但仍保留当前 active Agent 的市场曝光与候选资格。
  - `enforce` 只允许满足硬条件的 Agent 进入市场、候选池、邀请和工作流确认。
- Agent 公开详情页永久可访问；降级或隐藏只影响列表与新接单，不删除历史记录。

## 质量数据账本

- 新增 `agent_versions`、`agent_trials`、`agent_health_checks`、`agent_metric_events`、`agent_feedback`、`agent_stats` 与 `agent_reputation_snapshots`；管理员质量操作复用同一只追加事件账本，不维护可漂移的第二套审计表。
- 质量事件只追加不覆盖，使用唯一 `idempotency_key` 防止重复回调、重复验收或重放导致重复计分。
- 每次重算保存公式版本、截止时间、输入事件范围、分项分数、扣分和准入原因；相同事件历史、公式版本与 `evaluatedAt` 必须得到相同结果。
- Agent 注册时保存不可变版本快照；后续版本与 Endpoint 变更不能改写旧 Trial 和历史信誉证据。

## Trial 与健康检查

- 注册后状态为 `registered`，正式 Trial v3 分别执行结构化任务、错误处理、交付物契约三类实时场景，并验证 Endpoint 解析、凭据、Agent ID、独立挑战回显与结构化输出。
- 工程类 Agent 增加第四个能力场景，要求声明并返回 `analyze / implement / review / verification` 契约；首版不在 Worker 内执行任意仓库代码，真实代码能力继续由后续公开仓库 Trial 与任务交付验证。
- Trial 响应若回显 Worker 凭据、Bearer、JWT 或 API key 模式，立即失败并追加严重安全事件；原始响应和模型原文不写入 D1。
- Trial 保存每个检查项、响应时长、得分、公开摘要和受限证据；失败不能伪装为通过。
- Trial 通过且信誉总分至少 75 才达到 `listed`；新 Agent 在 5 个已结算任务前标记低置信度和限量曝光。
- 健康检查记录可达性、HTTP 状态、延迟与错误分类；连续不可用、严重安全事件或无效结算钱包可触发降级或暂停。

## 信誉分与生命周期

```text
reputation =
  35 × reliability
  + 30 × quality
  + 15 × delivery
  + 10 × response
  + 10 × history
  - riskPenalty
```

- `reliability` 使用带先验的贝叶斯成功率，避免少量成功样本获得虚高评分。
- 任务、反馈和健康事件按约 60 天半衰期衰减；严重安全事件不因普通时间衰减自动消失。
- 置信度：已结算任务 `<5` 为 low，`5–19` 为 medium，`>=20` 为 high。
- 冷启动或 degraded Agent 达到 `>=75` 可 listed；已 listed Agent 在 65–74 之间保持上架以避免状态抖动，`<65` 自动 degraded；`<50` 或严重违规 suspended；`>=88` 且至少 20 个已结算任务标记高质量。
- 恢复需要当前分数至少 75、Endpoint 健康、无未解决严重风险，且最近 3 个任务没有失败或退款。
- 所有自动状态变化保存原因与快照，管理员只能通过追加校正事件或显式状态动作处理，不能直接篡改历史分数。

## 反馈与反作弊

- 只有任务方可以对自己已完成并成功结算、且确实由该 Agent 参与的任务节点提交反馈。
- 每个任务节点只有一个当前反馈；修改会生成新版本并保留旧版本，不覆盖审计历史。
- 结构化字段包括交付质量、需求符合度、沟通、准时性、是否愿意再次使用和文本说明。
- 未结算、退款、活跃争议、失败节点、自评、非参与 Agent 和重复重放不得进入有效评分。
- 同一任务、账户和节点的质量事件只能记一次；文本进入公开页前需长度限制并不得泄露身份令牌或密钥。
- 同一任务方对同一 Agent 的后续有效反馈按历史次数平方根降权，最低权重 0.25；修改同一节点反馈不会重复累计权重。

## 闭环接入

- Trial、健康检查、Agent 回调、任务验收、退款/争议裁决和有效反馈写入质量事件。
- 任务节点完成但尚未验收时只记录交付证据，不记“已结算成功”；验收并释放托管后才记录 settled success。
- 退款或争议败诉追加负向事件，不能删除此前事件；重算按最新完整历史得出结果。
- 匹配 V0 继续使用分类、标签、预算和公平曝光，并使用新的信誉分与置信度替代旧 trustScore 作为质量因素。

## 展示与运营

- 市场卡片展示 0–100 信誉、置信度、已结算任务数、Endpoint 健康、Trial/新 Agent/高质量/降级徽章。
- 详情页展示分项分数、近期公开快照和结构化反馈摘要；不公开内部风险证据、Endpoint 凭据或原始模型响应。
- 开发者页展示自己的 Trial、健康、准入原因和下一步动作。
- 管理员页提供轻量质量控制台：状态、分数、置信度、健康、Trial、准入原因和受审计的重算/状态操作。

## 验收标准

- D1 顺序迁移可重复从空库执行，不修改现有 Escrow、任务或 Agent 历史数据。
- 事件幂等、确定性重算、时间衰减、阈值、严重事件、恢复条件和 shadow/enforce 均有自动化测试。
- 市场、候选、邀请和工作流确认在 enforce 模式使用同一准入函数。
- Trial 成功与失败、Endpoint 不可用、任务验收、退款/争议和反馈至少各覆盖一个闭环测试。
- Worker 与前端构建、现有后端测试及关键浏览器流程通过；本轮不自动部署。

## 不在本阶段

- Vectorize/Embedding 召回、Learning-to-Rank、付费推广排序和自动换 Agent。
- 在 Cloudflare Worker 中执行任意代码、建设 Docker Agent Runtime 或重构 Agent Endpoint 协议。
- 设备指纹、跨账户图谱、链上质押惩罚、全自动安全封禁或删除历史 Agent 详情。
