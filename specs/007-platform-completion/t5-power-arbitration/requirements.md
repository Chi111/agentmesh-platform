# T5 Power 仲裁、上诉与执行队列需求

## 目标

在不改变现有托管合约、不让 Worker 持有运营私钥的前提下，为任务争议增加显式版本化的 Power 加权投票、至多一轮上诉和可审计执行队列，同时保持既有一人一票案件兼容。

## 必须行为

- 创建首轮提案时管理员必须明确选择 `one_person_one_vote` 或 `power`；缺省保持一人一票兼容。
- 每个提案记录不可变的权重算法版本；首版仅允许 `one_person_one_vote.v1` 和 `member_power.v1`。
- 提案创建时冻结无利益冲突的委员资格、Power 和实际票权；后续委员状态或 Power 变化不得追溯改变既有提案。
- Power 模式的法定人数、支持、反对和弃权均按冻结票权计算；一人一票模式继续每名委员一票。
- 首轮提案和投票必须永久保留，不得被上诉覆盖。
- 首轮定案后开启 72 小时上诉窗口；窗口内未上诉时，首轮结果不得提前进入资金执行队列。
- 每个争议最多一轮上诉；上诉人必须是争议发起人、任务方或涉案 Agent 所有者，并提交至少 20 个字的理由。
- 上诉提案沿用首轮权重模式和算法版本，委员快照必须包含首轮委员并至少新增一名当前活跃、无利益冲突的委员；无法扩大时拒绝创建。
- 上诉创建和首轮提案创建都必须具备并发唯一性；重复或竞态请求不得产生第二个首轮/上诉提案。
- 最终可执行结果只能来自已定案的上诉提案，或来自上诉窗口已关闭且未上诉的首轮提案。
- 任务争议执行必须先写入持久化、幂等的治理执行队列；队列动作只能由最终提案结果推导，调用方不能自行选择相反动作。
- 执行队列必须同时校验争议仍在审核、托管仍被冻结、最终提案未执行；实际 Web3 资金动作继续由管理员钱包签名并由 Worker 验证交易。
- 队列模型预留 `ecosystem` 分域，但 T5 只允许任务争议入队；Governor/Timelock 允许列表和真实执行由 T10 完成，禁止 Worker 直接调用任意目标合约。

## 可观察验收

- 仲裁 API 返回当前提案、完整轮次历史、每轮冻结委员/票权/投票、上诉资格/期限和执行队列状态。
- 仲裁页可选择首轮投票模式，清晰显示算法版本、Power 票权、首轮与上诉历史、上诉入口和执行队列状态。
- 测试覆盖一人一票兼容、Power 计票/法定人数、快照冻结、利益冲突排除、上诉身份/期限/次数/扩大委员门禁、并发唯一性、窗口内禁止执行、队列动作推导、托管冻结门禁和交易验证边界。

## 明确排除

- 自动托管私钥、Worker 代签、任意合约调用、主网或测试网部署。
- 多轮或无限上诉、上诉期间修改首轮投票、按实时 Power 重算历史提案。
- Governor/Timelock 合约、Escrow v2、保证金、罚没或新的经济参数。
