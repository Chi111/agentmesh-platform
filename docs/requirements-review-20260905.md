# 需求与实现复盘（2026-09-05）

范围：当前工作区（包含既有未提交的匹配 v2、双边协作和仲裁报酬改动）。这是本地代码核查，不代表线上部署验收。

## 产品主线与验收口径

平台的核心价值是可验证的任务交付。需求应沿同一条用户旅程组织：明确目标与验收标准 → 有证据的团队推荐 → 双方接单 → 托管 → 执行与变更 → 成果验收 → 结算或争议 → 双盲互评。PM 激励和 3D 展示服务于这条主线。

| 环节 | 必须成立的业务规则 | 当前判断 |
| --- | --- | --- |
| 创建 | 时间、预算、产物与验收标准可被后续流程读取和执行 | 本轮补齐具体截止时间；验收标准仍需用户在编排中检查 |
| 推荐 | 先验证能力证据和容量，再排序；无可行方案不能伪装成功 | v2 已具备规则，但现有 Agent 需要先补齐审核证据 |
| 接单/托管 | 邀请绑定版本，接单完成后才能锁定实际报价 | 已有门禁与并发测试；拒绝、过期后的重新组队仍是关键体验 |
| 执行 | 当前 attempt 的结果单调提交，变更与返工留痕 | 已有实现；改期与费用变更不能直接修改已托管承诺 |
| 交付 | 用户得到可使用的成果包，内部 JSON 不算最终成品 | 官方运行时生成成果包；通用验收门禁仍需加强，见 P1 |
| 争议 | 沟通不自动冻结资金，资金案件走独立授权 | 双边协作已明确分开；目前仅整笔退款/解冻 |
| 互评/激励 | 双盲、期限明确、取消不计信誉、报酬不取决于投票方向 | 新实现已有覆盖，应同步到主 PRD 并监测实际使用 |

## 下一步优化，按优先级排序

### P1：把完整成果包要求落实为统一验收门禁

证据：`backend/src/deliveryPolicy.ts` 的 `workflowDeliveryReadiness` 检查全部节点完成、有效结果及 Implement 节点的当前 attempt 制品；该函数本身没有检查完整任务成果包。PRD 4.7 要求完整成果包，旧 5.7 却只要求至少一个交付物。官方发布路径会生成成果包，但这不能代替所有第三方回调、人工提交、重新验收入口的统一约束。

建议：先定义可验证的成果包标识、必需文件和来源，再为新任务引入版本化策略；统一在进入验收及释放前验证。旧任务采用明确 legacy 策略。验收测试应包括：只有阶段制品不能验收、旧 attempt 成果包不能验收、合法成果包可验收、旧任务兼容。不能仅凭文件名或非 JSON MIME 推断完整交付。本轮记录缺口，不直接改变已有任务结算规则。

### P1：计划过期后必须有可恢复路径

证据：`worker.ts` 已在确认推荐/方案时校验时间，但创建后没有明确的任务截止时间编辑入口；现有 change-request 处理阶段返工与验收标准，不能充当时间/资金修订接口。

建议：未托管任务可修改截止时间，并使推荐快照和旧邀请失效；已托管任务使用双方确认的变更单，记录工期、费用和验收标准的差异。先做未托管改期，避免用户只能重新创建任务。新增费用或节点部分退款另行设计资金状态机。本轮不暗中自动延长截止时间。

### P1：让关键协作动作及时触达

证据：`collaboration.ts` 当前问题/回应/互评命令没有接入现有通知投递路径。用户可以在面板读取记录，但不能假设已收到主动提醒。

建议：复用站内通知/outbox，覆盖新问题、回应、48 小时可升级、评价揭示及履职审核结果；事件键去重，按用户偏好发送邮件。密封评价通知仅包含“已提交”，不得泄漏正文或评分。验收以重复执行不重复提醒、跨开发者不泄漏为准。

### P2：统一待办，而不是让用户逐页找状态

任务列表应逐步提供“待我处理”：待接单、待托管、人工 Gate、失败重试、待验收、协作升级。由 API 提供结构化行动原因；当前 `missionStatusMeta` 还根据 `currentStage` 文案识别待托管/拒绝，文案调整可能改变状态标签。不能只增加更多前端字符串判断。

### P2：协调队列分页及运营指标

证据：`collaborationStore.ts` 管理员升级问题查询固定 `LIMIT 200`，无游标。量大时后续案件不可见。

建议：稳定 `(created_at,id)` 游标、状态/超期筛选；统计完成率、首次合格交付率、组队无方案率、验收到结算时间、争议处理时间。明确分母、时间范围和测试任务过滤，先采集实际基线再设目标，不使用未经校准的推荐分数作为成功概率。

### P2：持续构建检查与文档整理

Worker dry-run 不等于完整 TypeScript 检查，已有文档记录独立类型检查问题。应在专门任务中建立 backend tsconfig、修复基线并进入 CI。保持业务行为变更与大文件拆分分开；优先按命令/状态机边界拆分 `worker.ts`，不按文件行数机械拆分。

主 PRD 应记录稳定业务规则；CID、地址、发布记录移至部署文档，避免过期信息被当成线上事实。匹配审核、协调与奖励预算的运营责任也应指定到角色。
