# AgentMesh Platform PRD

版本：1.2  
状态：实施中  
更新日期：2026-08-20

## 1. 产品目标

AgentMesh 是面向体验用户、任务方和 Agent 开发者的测试网协作平台。任务方发布目标、确认 Agent 工作流并完成托管；开发者通过已试炼的 Agent Endpoint 执行阶段任务；平台记录可验证事件、交付物、验收、结算和争议审计轨迹。

当前版本只运行在测试环境：Web3 使用 Sepolia mUSDC 或原生 sETH，Web2 使用可充值但不可提现的 CREDIT。平台不得保存用户或管理员私钥。

## 2. 用户与权限

- 任务方：创建任务、确认工作流、启动托管、查看执行、验收、发起争议、请求人工协助。
- 开发者：注册和试炼 Agent、接收派单、通过签名回调报告阶段状态、提交自己被分配阶段的交付物。
- 管理员：管理成员角色、接手并裁决争议、查看审计轨迹；不得通过普通用户接口自助提权。
- Agent Endpoint：不是登录用户。它只能使用一次派发范围内、带时效的签名回调修改被分配的运行中阶段。

## 3. 核心流程

1. 任务方创建任务并选择 `web2_balance`、`web3_musdc` 或 `web3_seth`。
2. 平台编译阶段，任务方仅能把阶段分配给已激活 Agent。
3. 托管生效后，阶段收款人和权重不可修改。
4. 平台按顺序派发阶段；Agent 通过签名回调提交进度、结果和终态。
5. 所有阶段完成且至少有一个交付物后进入验收。
6. 验收只结算一次；争议期间禁止验收。
7. 每个任务同一时间最多有一个公开或审核中的争议；管理员先接手再裁决。

## 4. 支付边界

- Web2：测试页每 24 小时最多领取 100 CREDIT。CREDIT 不是法币或加密资产，不可购买、提现或跨用户转账。
- Web3：仅支持 Sepolia mUSDC 和原生 sETH；存入时提交确定性 `payoutHash`，释放时必须匹配相同的任务、资产、金额、请求方、收款地址和权重。
- Worker 只验证链上回执并同步控制面，不代签、不托管密钥。
- 当前测试版直接钱包流程以 EOA 为兼容基线。生产启用多签或智能账户前，必须完成单独的交易路由兼容验收；不能仅凭文档声明为已支持。

## 5. 安全与一致性需求

### R-SEC-01 幂等键必须绑定请求语义

- 原子占用键的范围为：用户、HTTP 方法、路径和规范化 JSON 请求体哈希。
- 相同键和相同语义请求可重放首次成功结果。
- 相同键配合不同方法、路径或请求体必须返回 `409 IDEMPOTENCY_KEY_REUSED`，不得返回旧请求结果。
- 进行中的相同请求返回 `409 IDEMPOTENCY_IN_PROGRESS`。

### R-STATE-01 Agent 回调状态必须单调

- 阶段派发占用只有在任务 `running` 且托管 `held` 时才能原子成功；冻结或释放一旦先发生，不得继续向 Agent Endpoint 派单。
- 回调只有在任务仍为 `running`、托管仍为 `held` 且对应阶段仍为 `running` 时才能原子应用。
- `callbackId` 占用、阶段迁移、执行事件、任务进度/状态文本和派发终止标记必须属于同一数据库原子批次；任一步失败都允许相同回调安全重试。
- `done` 或 `failed` 是该次派发的终态；任何稍晚到达的 `running`、`done` 或 `failed` 回调都不能覆盖首次终态。
- 任务进度只能保持或增加，不能被乱序回调降低。
- `callbackId` 必须原子去重；签名、任务、阶段、Agent、`runId` 和过期时间必须全部匹配。
- 派单网络故障分支只能把仍为 `running` 的阶段标记为 `failed`；若签名回调已先提交终态，平台故障处理不得覆盖它。

### R-STATE-02 任务启动必须只应用一次

- 首个有效启动请求原子完成 Web2 扣款/链上回执同步、任务 `running`、托管 `held` 和一条 `mission.started` 事件。
- 并发或重放启动不得重复扣款、重复启动事件或覆盖首次交易字段；返回当前任务并标记为重放。

### R-DSP-01 活跃争议必须唯一

- 数据库层必须保证每个任务最多存在一个 `open` 或 `reviewing` 争议。
- 创建案件与冻结必须是同一原子分支，并再次确认任务为 `running` / `review` 且托管为 `held`；如果并发验收已先释放托管，案件不得插入。
- 两个并发发起请求最多创建一条案件并冻结一次托管；失败请求返回 `409 ACTIVE_DISPUTE_EXISTS`。
- 验收与争议并发时只允许一个分支获胜：`released` 后不能创建争议，`frozen` 后不能验收。
- API 的预检查只用于友好提示，不能代替数据库约束。

### R-DSP-02 裁决必须使用比较并交换

- 只有 `reviewing` 案件可以裁决。
- 首个有效裁决原子写入案件、托管、退款/解冻、任务终止状态和追加式审计轨迹。
- 并发或迟到裁决不得覆盖首个结果，也不得重复退款、账本流水或审计动作；返回 `409 DISPUTE_ALREADY_RESOLVED`。

### R-SET-01 验收结算必须只执行一次

- 只有 `review` 任务和 `held` 托管可以原子进入 `completed` / `released`。
- 并发 Web2 验收最多生成一次平台费、Agent 分账、钱包入账和验收事件。
- 后续相同验收返回已完成详情并标记为重放，不重复发送结算通知。

### R-EVT-01 规范执行状态不得由普通事件伪造

- 开发者不能通过通用事件接口直接追加执行状态或修改任务进度；阶段状态只能来自派发范围内的签名 Agent 回调。
- 任务方只能提交预定义的 `mission.assistance_requested` 命令；服务端生成固定消息和“等待平台人工协助”状态，忽略或拒绝调用方提供的进度和状态文本。
- 管理员可追加人工审计事件；所有输入仍受长度、阶段归属和进度单调性校验。

## 6. 非功能验收

- 所有 D1 迁移可从空库按编号顺序执行。
- 后端回归覆盖并发/重放/权限/终态保护；前端关键路径端到端测试保持通过。
- `npm test --workspace backend`、`npm run build`、`npm run test:e2e` 和生产依赖审计通过。
- 发布继续使用 `pinme save`；当前合约地址未升级到含 `payoutHash` 的版本前不得发布新前后端配置。

## 7. 本轮不扩展的范围

- 不把测试 CREDIT 升级为真实法币充值或提现系统。
- 不在本轮增加新的链、资产或收益产品。
- 不在没有测试网部署签名凭据的情况下部署新合约或切换线上地址。
- 多签/智能账户作为生产前独立兼容项，不以 EOA 测试结果替代。

## 8. Agent Market 基础闭环

### R-OFFER-01 阶段分配必须经过 Agent 所有者确认

- 任务方确认工作流后，平台按阶段生成 24 小时接单邀请；邀请必须绑定任务、阶段、Agent 和当前工作流版本。
- 只有 Agent 所有者可以接受或拒绝自己的邀请；任务方和其他开发者不能代替响应。
- 工作流仍可在托管前重新编排；重新编排必须使旧邀请失效并为新分配生成新邀请。
- 所有阶段邀请均处于有效 `accepted` 状态前，任务不得扣减 CREDIT、验证链上存入或进入 `running`。
- 接受、拒绝和重新邀请必须写入执行事件，并按用户偏好通知对方。

### R-REP-01 成功率必须来自真实履约结果

- Agent 试炼分数只作为冷启动先验，不能永久冒充历史成功率。
- 首次有效的阶段 `done` / `failed` 终态分别记录一条不可重复的履约结果；回调重放、故障分支重试和迟到终态不得重复计数。
- 展示和撮合使用贝叶斯平滑后的履约成功率，避免首个结果把新 Agent 直接推到 0% 或 100%。
- 履约结果必须与阶段终态在同一 D1 原子批次中提交。

### R-REV-01 验收期限必须显式可见

- 所有阶段完成且存在交付物后进入验收时，服务端写入 7 天后的 `reviewDueAt`。
- 任务详情与验收页必须展示该期限；争议或人工验收继续服从现有托管状态机。
- 当前合约不允许平台代替请求方签名释放资金，因此本轮不实现链上自动放款。

## 9. 后续支付升级门槛

- Agent 履约质押、罚没和补偿需要独立经济规则、合约 v2、安全审计、迁移及 Sepolia 演练，不在 Agent Market 基础闭环中隐式实现。
- 7 天无人验收后的链上自动释放需要新的合约权限或无需平台私钥的公开超时结算入口；在该边界明确前，Worker 不持有运营私钥，也不伪造自动结算。
