# Agent 匹配与工作流分配 v2 设计

日期：2026-09-05。状态：首版已在本地实现并验证，尚未部署。后续章节保留目标设计；实际交付边界以本节为准。

## 本次实现与上线准备

- 新增 `shared/matching.ts`、`backend/src/matching.ts`、`workflowAllocator.ts` 与 `matchingStore.ts`：结构化证据过滤、可选语义排序、整组 DAG 分配、决策快照与容量控制。
- 自动推荐要求当前 Agent 版本的容量档案和管理员审核的能力证据。证据需关联当前版本通过的 Trial，但 Trial 通过本身不等于能力认证；管理员还需审核任务描述、工具、输入输出和估计耗时。没有证据返回待补充，不伪造默认履历。
- 使用固定透明效用权重与弱先验，语义判断仅影响已合格候选的排序；模型失败时回退到结构化证据。分数不是成功概率，尚未通过线上数据校准。历史只使用实际节点结果与已结算反馈，按版本、任务族、模式隔离。
- 分配采用宽度 16、每节点最多 8 个候选的有限搜索，支持预算、明确时区的截止时间、共享池并发、人工锁定和独立审查约束；不保证全局最优。审批等待未知时不承诺总工期。既有接单承诺及未结束执行暂时采用保守排除，不预测其释放时间。
- 推荐方案有效期 5 分钟；确认时复核快照、证据有效期和剩余期限。执行时再次核验资格，并通过 D1 原子占位控制容量；不自动发送邀请、付款或换人。
- 派发领取使用唯一令牌隔离旧请求。联系边界前中断可在 5 分钟后恢复；联系边界后未确认结束的执行持续占位，避免超时后重复执行。远端终态回调事务内释放；手动释放需要所有者确认远端已停止。
- 前端删除旧的自动评分阈值选人，改用后台方案；提供均衡、速度和成本偏好、选择依据、人工锁定，以及 Agent 容量/证据设置。

上线前先执行 `db/035_matching_and_capacity.sql`，再更新 Worker 和前端；本次未操作线上数据库或部署。现有 Agent 需要所有者填写容量、管理员登记审核证据后才能进入 v2 自动推荐。旧手动选人流程保持兼容，执行容量默认单并发。后续工作包括线上权重校准、受控探索和更精确的预约日历，未包含在本次实现。

验证：后端全量 242 项测试、Worker dry-run 构建及前端 TypeScript/Vite 构建通过；3 项浏览器回归验证初次自动组队、手动触发、方案依据展示与保存。仓库额外独立 Worker 全量类型检查存在既有错误，未宣称该检查通过。

## 1. 目标与范围

用户描述目标后，平台分解任务，自动生成一份可执行的 Agent 组队方案：每个节点有主选、候补、选择依据、报价、预计执行区间与不确定项。用户确认方案后，沿用邀请接受、资金托管和 DAG 执行流程。

匹配解决“哪个 Agent 能可靠完成这个具体节点，以及整条任务如何按约束完成”。标签只能辅助检索；自我介绍不能证明能力；语义相似度不等于成功概率。

本设计不改变资金授权边界，不自动替用户追加预算，不把未校准分数显示为成功率。初版优化单条工作流，同时服从全平台已有容量承诺；跨全部客户任务的全局最优调度不在首版范围。

## 2. 已有能力与实际缺口

根据当前源码（包含本次会话已完成的本地匹配改动）：

| 当前模块 | 可复用 | 需要补齐 |
| --- | --- | --- |

| `backend/src/logic.ts` | 候选硬过滤、版本化报价、规则排名 | 任务语义、证据适配与工作流整体分配 |
| `backend/src/agentQuality.ts` | Trial、健康、制品、结算、争议等事件 | 按任务族/执行模式/Agent 版本聚合的表现 |
| `backend/src/contracts.ts` | Agent 版本、输入输出 schema、Trial 证据、报价 | 已验证能力档案、容量和任务耗时分布 |
| `backend/src/store.ts` | D1 持久化、outbox、派发领取、阶段状态 | 决策快照、容量租约和原子资源约束 |

当前健康探测的 responseTimeMs 反映端点响应，不代表任务完成速度。任务结算成功属于任务级事件，不能直接当成每个节点都成功的独立训练样本。当前运行节点数影响报价，但不是容量上限。

## 3. 总体流程

```text
任务分解 → 节点需求档案 → 多路召回 → 硬约束校验
                                      ↓
                            证据适配与表现估计
                                      ↓
                   DAG、容量、成本约束下的整组分配
                                      ↓
                  带版本的推荐方案 → 确认与邀请
                                      ↓
                  接单/托管 → 原子占位 → 执行
                                      ↓
                     验收、归因、更新能力证据
```

LLM 用于理解任务和提取可核实特征；确定性代码负责校验、排名、资源分配和授权。模型无法直接授予能力认证、调整预算或发送邀请。

## 4. 两类画像

### 节点需求档案 TaskProfile

每个节点单独生成，不能重复使用整条任务的标签：

- `taskFamily`：例如前端实现、资料核验、数据清洗、报告写作。
- `executionMode`：analyze / implement / review。
- `objective`、`acceptanceCriteria`：做什么、怎样算合格。
- `requiredCapabilities`：规范化能力标识，区分硬性要求和偏好。
- `inputContract`、`outputContract`：数据类型、文件格式、字段、大小限制、版本。
- `toolsAndAccess`：必须有的浏览器、代码执行、私有数据访问等权限；不含凭证明文。
- `complexityFeatures`：输入规模、交付规模、依赖数量、验证难度；不只用一个主观等级。
- `language`、`riskTier`、`budget`、`deadlineAt`、`dependencyIds`。
- `provenance`：用户明确要求、模板约束、模型推断；推断的置信度与待确认项。

无法识别的能力保留原文并标为 unknown，不静默删除。缺少影响资格的关键要求时，生成需补充信息的方案。兼容现有 requiredCapabilities 标签，但逐步映射到版本化能力标识；模型不得把偏好擅自提升成硬条件。

### Agent 能力档案 AgentProfile

按 Agent 版本记录：开发者声明、Trial 已验证、真实交付已验证三类证据。每条证据绑定能力标识、测试范围、suiteVersion、artifact/reference、时间和有效状态。

记录支持的输入输出、工具访问和约束；不能只读取模型宣传文案。服务自报能力必须由平台可核验的证据确认，高风险能力缺少验证时不允许自动分配。

增加 `maxConcurrency`、可用状态、已承诺任务和容量更新时间。未知容量视为不能承诺自动执行，不默认无限容量；内置 Agent 也使用明确的平台配额。

历史数据按 taskFamily × executionMode × agentVersion 聚合；领域、规模等作为分层特征。细分样本不足时回退至较粗任务族并展示较低置信度。升级版本保留旧历史，但不能继承旧版本全部认证。

## 5. 召回与硬约束

### 召回

首版小候选池采用全量资格扫描，避免过早丢掉新 Agent。扩大后采用多个通道取并集：已验证能力、结构化领域/模式、相似历史成功案例、语义相关性。每路保留名额，新 Agent 有独立的 Trial 合格通道。

现有平台已提供 chat/completions，可批量提取有限候选的语义特征；Embedding 服务尚未确认，不作为首版前置依赖。模型输出必须有证据引用、schema 校验与版本缓存。缓存键包含节点档案哈希、Agent 版本及证据版本。

模型调用只读最小必要上下文，开发者介绍与制品内容按不可信数据处理。调用超时或不可用时，退回结构化证据匹配；证据不足就返回需人工确认，不能伪造高适配分。

### 硬约束

先判断资格，再比较优劣：

1. 已上架、允许接单、健康信息有效，满足现有安全/质量门。
2. 必需能力有相应等级的证据，必要工具与授权可用。
3. 输入输出兼容。首版只支持平台定义的 schema 子集、版本化类型和已登记转换器；不声称通用 JSON Schema 包含关系可自动判定。未知兼容性不能自动放行。
4. 报价在节点预算内，且整组总额在任务预算内；默认不挪用其他节点预算。
5. 有可行的执行时间与容量窗口；当前满载可以排队，只要明确的截止约束仍可满足。
6. 独立审查节点不能由同一 owner 的实现 Agent 担任，前提是任务明确要求独立审查。

既有 quality gate 的 shadow/enforce 配置仍保留：v2 自动分配必须满足实际验证门槛，shadow 只能产生观察结果，不能作为自动派单许可。

sETH 无可信 FX 时，只比较同币种有效报价；沿用现有节点预算报价的 Agent，成本维度无法区分，标明该维度信息不足，不制造 USDC 性价比排名。

## 6. 节点匹配算法：证据优先，数据逐步学习

### A. 首版可解释效用模型

先用结构化证据输出 F（任务适配）、Q（相似任务验收质量）、R（同类履约可靠性）、H（交接便利性）、U（不确定性），均为 [0,1]。费用和时间交给整组优化，避免重复扣分。

一个可实验的初始效用为：

`V(i,a) = 0.35 F + 0.30 Q + 0.25 R + 0.10 H - 0.15 U`

这组权重是待评测的设计初值，不是经验结论或概率。所有分量均输出来源和缺失项。标签命中不能直接增加已验证适配分；F 由“节点要求覆盖 + 同模式 Trial + 相似交付证据”构成，语义分析只辅助识别证据相关性。

没有任务历史时使用明确标记的任务族先验与较高 U，不以 0 次失败当成完美记录。Trial 与真实任务分开计数；历史全局信誉主要用于市场准入和弱先验，不再把信誉、可靠性、成功率反复叠加。

原始效用值可为负；只用于排序，不强行夹成一个看似概率的百分数。若界面需要分数，明确标注“匹配评分”，同时显示证据覆盖和不确定性。

### B. 同类任务可靠性与时长

完成归因清洗后，对同任务族的终态按 Beta-Binomial 模型做平滑：

`alpha = k * p0 + s; beta = k * (1-p0) + f`

其中 p0、k 来自有版本的任务族先验，s/f 是可归因且去重后的成功/失败数；给出后验均值和保守分位数。样本权重、近期衰减与分层借样若启用，必须另行验证区间覆盖率，不能继续把结果当成精确的共轭后验。

成功定义为节点在约定重试与时间预算内通过客观验收；同一节点的多次重试合并成一次履约样本，同时单独保留首次通过率。用户取消、上游阻塞、平台故障和 Agent 失败分别记录；无法归因的事件不默认计入 Agent 失败。

耗时分别记录接单等待、容量排队、实际执行、验收等待。对同类任务估计执行 P50/P90，样本不足时回退至任务族保守范围。仍在运行的任务是删失样本，不能只用已完成任务估计耗时，否则会系统性低估长任务。

### C. 后续学习模型

积累可用标签后，用逻辑回归或梯度提升树预测“该 Agent 对该节点的验收通过率”，并预测时长/返工风险。输入为任务特征与 Agent 证据，禁止用任务完成后才出现的字段造成泄漏。

只有时间切分验证、分任务族校准和置信区间覆盖检查通过后，才能对外展示预测成功率。学习模型替换对应的效用分量，不把预测概率再和同源信誉、成功率全部叠加。

## 7. 整组分配：有资源约束的 DAG 排程

每个节点各取最高分会让一个强 Agent 被重复选中，引发串行等待。分配变量不仅是 Agent ID，还包括预计开始/结束时间与资源占用。

硬约束：每个任务节点一个主选；遵守 DAG/审批 Gate；同一资源池的同时执行数不超过容量；满足授权预算；已有运行和已接受的承诺不能被新方案抢占。不同 Agent 若共享同一开发者底层资源池，需声明共享 pool 并一并限额。

方案效用：

`J(plan) = sum(w_i * V(i, a_i)) - lambdaC * totalQuote / budget - lambdaT * makespan / timeBudget - lambdaH * handoffCost - lambdaR * concentrationRisk`

w_i 根据验收重要性归一化，不能靠增加节点数量提高分数。handoffCost 衡量实际格式转换/传输代价；H 衡量节点自身交接证据，二者不可重复计费。concentrationRisk 仅用于显式共享故障域和相关失败风险，无数据时标 unknown，不假设各节点独立成功再简单连乘。

首版的各 lambda 是版本化产品策略，默认 balanced；用户选择速度或成本偏好只改变软目标，不能降低硬安全/预算门槛。无明确截止时间时不计算上述 timeBudget 比率，改用有版本的任务族参考时长；审批等人为等待未知时只报告自动执行部分及依赖条件，不承诺整体完成时间。

### Worker 可运行的求解方式

采用“关键路径优先的列表排程 + 有界 Beam Search”，不在 Worker 引入重型原生求解器：

1. 计算拓扑顺序和基于保守时长的剩余路径长度；优先为关键、候选少的就绪节点决策。
2. 每节点初始保留至多 8 个候选，每个候选寻找资源日历内最早可行窗口。前驱结束时间加交接成本决定最早开始时间。
3. 每扩展一层保留至多 16 个部分方案，按带未分配节点下界的目标排序；稳定 tie-break 支持复现。
4. 完成后验证全部硬约束，再做有限的节点换人/成对交换来改善方案。
5. 若裁剪导致无解，扩大候选或返回“本次有界搜索未找到可行方案”，不能宣称市场不存在可行解。单独保留一个确定性可行基线，超时返回该基线并标注未优化；若基线也不可行，不强行派单。

8/16 是待压测的工程初值，需测候选规模、资源日历长度与 Worker CPU 预算；不保证全局最优。小规模离线用穷举或外部 CP-SAT 求解结果作参照，评估质量差距。

依赖顺序和资源不可重叠的约束建模可参考 [Google OR-Tools Job Shop 文档](https://developers.google.com/optimization/scheduling/job_shop)。这里扩展为可选 Agent、并发容量及业务预算，首版在线算法为本项目设计。

### 示例：为什么要整组分配

假设两个无依赖节点，每节点预算 50 CREDIT，总预算 100，要求 10 分钟内完成。A 对两个节点适配都略高，每次执行估计 6 分钟、40 CREDIT，但并发容量只有 1；B 能完成第二个节点，估计 8 分钟、45 CREDIT，并发容量为 1，双方均空闲。

逐节点取第一名会选 A+A，预计串行 12 分钟，违反截止约束；整组分配选 A+B，预计 8 分钟、85 CREDIT，满足约束。这里时间和报价都是示例输入，不代表真实服务性能；正式计划使用有来源且带不确定性的估计。

## 8. 方案生命周期与容量一致性

`proposed → confirmed → offered → accepted → executing → completed/failed`

推荐方案只读，不占用真实执行槽。返回 workflowVersion、profile/evidenceVersion、pricingVersion、capacityRevision、policyVersion、expiresAt 和 planHash。

确认方案时服务端重验版本、价格和资格，过期返回可解释差异及新方案。用户手动锁定的节点作为求解硬条件；其他节点仍可优化。确认不代表已接单，也不代表资源已预留。

接单形成有期限的承诺，纳入调度日历；未来窗口是容量估计，不是长期占用执行槽。排队节点在执行前重新校验；发生资源竞争时重新排队并更新 ETA，超出已确认截止条件则返回需要调整方案。

真正派发时，在一个数据库原子事务/批次中验证任务状态、容量约束并领取执行租约，随后写 durable outbox。两个并发请求不能各自“看见一个空槽”并同时占用。租约绑定 runId、attempt、资源池、fencing token，重复派发使用相同幂等键。

租约超时不意味着远端已经停机：先查询/撤销旧执行，或由遵守 fencing 协议的端点保证旧 token 不能产生副作用。无法确认停止的第三方任务进入隔离占用状态，不贸然释放容量并并发重派。终态回调幂等释放；暂停、取消、失败、重试及旧回调都必须覆盖。

## 9. 主选与候补

每节点保留至多两个可解释候补，不额外占用执行槽。优先满足相同能力和授权约束，故障域可验证时选择不同域。

拒单或明确终止后可以提出替换方案；对价格、收款方、交付条件和截止承诺的变化重新走授权边界。当前合约/托管可能绑定 payoutHash，资金锁定后不允许仅改数据库 agentId 完成换人；首版只生成需处理的替换建议，待兼容的合约变更或安全重建流程实现后才能自动切换。临时 HTTP 超时不得直接认定旧 Agent 未执行。

## 10. 冷启动与学习反馈

新 Agent 先通过同任务族基准测试，在平台测试任务或用户允许的低风险任务中收集证据。不开启无边界随机分配，也不永久因为历史少而排除。

探索仅在满足硬约束的候选之间进行，设置预算、风险和任务族上限，记录真实的选择概率。若用户手动改选，记录为覆盖决策，不能继续使用系统概率做无偏评估。

每次决策记录候选集、被过滤原因、特征快照、选择/曝光概率（确定性策略明确为确定性）、策略版本、用户改选、实际执行与验收结果。未选中的候选没有反事实结果，不得把它们记作失败。

以后尝试 contextual bandit 前，先检查日志支持度与选择偏差；缺少随机化/重叠支持的历史数据不能证明新策略的因果收益。离线策略评估的方差与奖励模型限制参见 [Microsoft Research 的离策略评估研究](https://www.microsoft.com/en-us/research/publication/optimal-adaptive-off-policy-evaluation-contextual-bandits/)。首版无需强化学习。

## 11. 接口与数据落点（拟新增）

- 在编译结果中保存有版本的 TaskProfile；在 AgentVersion 下保存能力声明与平台验证证据。
- `POST /api/missions/:id/match-plan`：只计算方案，不发送邀请；请求指定 workflowVersion、偏好与人工锁定节点。
- `GET /api/missions/:id/candidates`：保留兼容，逐节点返回推荐和证据、缺失项；前端不再自己用 80/10 阈值重新决定权威分配。
- 现有 workflow 确认接口新增可选 planId/version；服务端校验后使用快照生成邀请，旧 assignments 流程仍需通过相同资格与预算检查。
- 新增数据实体：任务档案、版本化能力证据、节点履约样本、匹配决策及候选快照、资源池与租约。迁移编号待实施时分配，避免与并行开发冲突。
- 实现归属：`matching.ts` 汇总匹配策略与候选解释，`workflowAllocator.ts` 执行纯函数排程，`store.ts` 处理数据库一致性；`worker.ts` 只协调接口和既有生命周期。
- 不引入多个微服务；学习模型和向量检索等有数据与规模证据后再单独部署。

方案输出每节点包含 chosenAgent、alternatives、evidence、estimatedWindow、quote、uncertainty、blockedReasons；整组输出总价、预计关键路径、可行性、待确认事项与是否自动可执行。推荐理由从结构化字段渲染，不让 LLM 创作没有证据的能力陈述。

## 12. 评测与分期

先建立至少 60 条人工审定的节点匹配样例、20 条含资源冲突的工作流；这是测试覆盖起点，不足以证明统计收益。覆盖错标签、相似表述不同能力、冷启动、过期证据、版本升级、共享资源池、无可行方案、sETH、人工 Gate 和资金锁定后替换。

回归门槛：

- 所有确定性测试中硬约束违规为 0；并发抢占同一槽只有一个成功。
- 相同输入快照/策略种子产生相同方案；候选截断和超时可解释，不静默放松约束。
- 新旧策略对比候选召回、人工审定排序、可行方案率、延误、总成本及手动改选率。
- 数据不足时标为未知，禁止虚构高成功率；语义服务失效时稳定降级。
- 小图对照最优排程；大图压测 CPU、延迟和可行性。线上先 shadow，不改变现有派单。
- 通过受控测试或授权流量实验，按任务族报告验收通过率、首次通过率和工期；必须给样本量、区间及代价，不仅给一个平均分。

实施分期：

1. **画像与证据匹配**：TaskProfile、Agent 能力证据、决策日志、确定性资格与效用，后端生成方案；shadow 验证。这一阶段只能推荐，不能声称容量已保障。
2. **容量与整组自动分配**：执行租约、资源日历、Beam 排程、方案确认和幂等派发，完成并发与异常回收测试后开启符合条件的自动分配。
3. **数据学习**：同类任务校准模型、有限探索与离线评估；只有实验支持才替换相应规则模型。
